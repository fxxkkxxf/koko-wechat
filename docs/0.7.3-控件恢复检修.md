# 0.7.3 控件恢复检修

本次日志中的BG_ACCESSIBILITY发生在输入和发送之前。现场新建的只读连接可以读到输入框，但旧版恢复链路有两个缺口：普通wake只把无障碍标志设为1，不能覆盖「标志已经是1、实际子控件仍失联」的状态；当前页面只有会话列表时，也会因为缺少输入框而过早报接口不可用。

## 修复

- 继续先用标准订阅和现有桥接库唤醒。尚未恢复时，才进行受控的提供者重建。
- 仅使用已安装桥接库按当前DLL身份、PE特征和已验证缓存识别的候选地址，不硬编码某个微信版本的偏移。候选必须在已绑定微信模块范围内，当前值必须为0或1。
- 一次只尝试一个候选，最多四个。原值为1时短暂归零再置1，强制重新建立连接；以实际可读的输入框或会话列表为成功标准，不把根窗口类名、控件数量或库返回成功当成充分证据。
- 写入后回读核验；失败或中途取消则恢复原值，再决定是否尝试下一个候选。恢复失败停止后续尝试。全过程重新检查原有账号窗口和任务有效性，不自动改用前台、不重发消息。
- 当前页面已有可读取的会话列表时，可以打开唯一匹配且已经验证身份的目标会话，再核验输入框。可读的人工草稿继续保留；找不到唯一目标就停止，不猜测收件人。
- 已有较完整控件树但找不到聊天控件时，改报BG_CHAT_VIEW并提示回到聊天页。过期UIA元素也能进入发送前修复，和输入、发送后的故障区分处理。
- 失败记录保留恢复阶段和前后可读节点数，单条与分段发送均保留诊断。
- 「检测连接」通过真实桥接进程执行只读聊天控件探测，报告实际可读性；不仅检查微信窗口是否存在。探测不导航、不输入、不发送消息。

## 验证和限制

2026-11-09暂停助手后，对已绑定进程做一次受控重建验证：176个可读控件→短暂只有2个外壳节点→恢复176个控件，输入框恢复可读，原标志值保持为1，前台窗口不变。没有点击控件、输入文字或发送真实测试消息。

模拟回归另覆盖「标志已是1但树仍为空」、唤醒假成功、逐候选回滚、取消、无效候选、读取异常、非聊天页面导航、过期元素恢复及诊断传递。受控验证说明重建机制可用，不能证明已复现这次长期运行故障的全部条件，也不能代替实际送达验收。

发布回归：Node 276项通过；Python 163项中162通过、1项平台相关跳过。

自动回复、群选择、人设、模型和发送账本保留原配置；历史失败回复不会补发。若微信版本变更导致候选不适用，或窗口实际不在可用聊天页，仍会停止本次操作并显示原因。
